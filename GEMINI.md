# Project rules (flinttype) - Gemini CLI

flinttype is an open-source typing speed test, built on top of a generic Next.js + shadcn scaffolding base. Keep boilerplate-style scaffolding generic and reusable; product-specific code (typing tests, results, leaderboards) lives alongside it.

## Foundational Mandates
- **Next.js + shadcn** frontend.
- **Backend with middleware layer**, consumed via a `useBackend().route.methods` client abstraction.
- **Unit tests required** for every backend route.
- **Auto-commit every change.** No AI watermarks or attribution.

## Package Manager
Yarn classic (1.x), pinned in `package.json` (`yarn@1.22.22`). Always run `yarn`, `yarn add`, `yarn install`, `yarn test`, etc. — never `npm`. Lockfile: `yarn.lock`. No `package-lock.json`.

## Environment & Logging
- `APP_ENV` (`development` | `production`), `LOG_ENABLED`, `LOG_LEVEL` in `.env`.
- Secrets in `.env.local` (gitignored).
- Server-side structured logging via `src/server/logger.ts`. Use `ctx.log` (request-scoped) — never raw `console.*`.

## Commit Discipline
**At the end of every turn where you modified files, commit before yielding control.**

1. Stage only changed files (`git add <paths>`).
2. Read `VERSION` and bump it:
   - Patch (`0.0.X`) — default, small fix/docs/chore
   - Minor (`0.X.0`) — new user-facing feature
   - Major (`X.0.0`) — breaking change
3. Write the new version back to `VERSION` and include it in the stage.
4. Commit with Conventional Commits format:
   - Subject: `type(scope): short title` (feat, fix, chore, docs, refactor, test, build, style)
   - Body line 1: the new version (e.g. `0.0.2`)
   - Body: terse bullet list of changes.
5. **Strictly no AI attribution** (no "Generated by Gemini", etc.).
